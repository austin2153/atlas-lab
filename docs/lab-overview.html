Topology

Frontier fiber runs straight into the UniFi gateway, with no ISP router in between. The gateway routes between four VLANs: management for network gear, home, IoT and lab. The whole Proxmox host, Pi-hole included, sits on the lab VLAN with nothing tagged. Only the basement AP is wired; the other two mesh wirelessly because the house has no ethernet runs.

UniFi handles routing, Wi-Fi and DHCP. Every machine uses Pi-hole (192.168.20.3, on the lab VLAN) first, which filters ads and holds every *.atlas.local record, and Cloudflare 1.1.1.1 as a fallback so internet names still resolve if Pi-hole is down.

How service IPs work (MetalLB)

On a home cluster there's no cloud load balancer, so a Kubernetes service of type LoadBalancer would wait for an address forever. MetalLB fills that gap:

  1. The controller hands out an address

    One controller pod watches for LoadBalancer services and gives each one an address from default-pool (192.168.20.50–.99), or the exact one the service asks for.

  2. A speaker announces it on VLAN 20

    A speaker pod runs on every node. In Layer 2 mode, one of them answers ARP for each service address ("that IP is me"), so the gateway and your Mac send traffic for it to that node. If the node goes down, another speaker takes over within seconds.

  3. The node forwards to the pods

    Kubernetes passes the traffic from that node to the service's pods, wherever they run in the cluster.

To give a new service an address, set type: LoadBalancer and pin the next free address from the table above. The config lives in platform/metallb/l2-config.yaml; the full refresher is in docs/architecture.md.

apiVersion: v1
kind: Service
metadata:
  name: my-app
  annotations:
    metallb.io/loadBalancerIPs: 192.168.20.51   # next free
spec:
  type: LoadBalancer
  selector:
    app: my-app
  ports:
    - port: 443

How it gets built

  1. Terraform creates the cluster

    The bpg/proxmox and siderolabs/talos providers download the Talos ISO, create the three VMs on VLAN 20, apply the machine configs and bootstrap etcd. State lives in Terraform Cloud, but runs execute locally so they can reach the private network.

  2. ArgoCD installs the platform

    One root ApplicationSet watches platform/. To add a service, I add a folder and push to main. It's live within a few minutes, with self-heal and prune enabled.

  3. Kratix and Flux handle self-service requests

    A request such as "give me a Proxmox VM" goes through a Kratix promise pipeline. The pipeline writes manifests to state/ in Git, and Flux applies them to the cluster.
